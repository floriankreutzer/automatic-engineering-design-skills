# Planning and design systems

Modified adaptation of Impeccable 4.9.1 shape, new-work, document and extract principles. No runtime or generated service is required.

## Shape the work

Establish the audience, job, success condition, available content, main actions and constraints. Reuse reliable project context. Resolve only questions that materially affect the result; do not repeat settled choices.

Describe a compact brief covering the target surface, visitor mode, task sequence, information hierarchy, supported states, content extremes, responsive intent and delivery constraints. For a planning-only request, deliver the brief without editing the application.

## Determine visual authority

Read existing tokens, components, screens and approved references. Documentation is one source of authority, not the sole source. A missing design document does not justify replacing the current identity.

Distinguish three kinds of work:

- **Refine:** preserve the identity and improve execution within it.
- **Extend:** express the existing system on a new surface, adding only the patterns the new task requires.
- **Redesign:** change the visual language because the user requested it, while preserving product facts, functional needs and applicable constraints.

When the brief fixes colors, fonts, materials or composition, honor that direction. General advice about avoiding common patterns does not override an explicit brand requirement.

## Develop a concrete direction

State one clear structural idea: what leads, what follows, how the user moves through the information, and where the primary action appears. Choose type, spacing, color, imagery and motion as a coherent response to that idea.

Use real content and approved assets. Present alternatives only when a consequential design choice remains open or the user asks for options. Keep alternatives comparable in scope and fidelity, explain their tradeoffs and distinguish proposals from approved decisions.

For operational interfaces, favor recognition, consistent controls and efficient paths. For marketing and expressive surfaces, let the approved concept carry more visual character while preserving clarity and truthful content.

## Document the implemented system

When documentation is in scope, record observed or implemented tokens, semantic roles, type hierarchy, spacing, components, state behavior, responsive patterns and relevant rationale. Match the project's existing documentation structure.

Differentiate established rules, deliberate exceptions and unresolved decisions. Do not describe an aspirational system as already implemented. Keep documentation aligned with code and representative evidence.

## Extract reusable patterns

Look for repeated behavior and shared purpose, not merely similar shapes. Prefer an existing component or token before introducing a new abstraction. Choose the narrowest reusable boundary that removes real inconsistency.

Preserve accessibility, state coverage and functional contracts while consolidating. Check representative consumers, including unusual content and responsive contexts. Avoid sweeping unrelated refactors during a small design task.

## Complete the handoff

Connect the chosen direction to specific changes and acceptance criteria. Identify evidence needed for review, required regression and progression checks, and any unresolved dependency. For implementation requests, continue through the normal project process within the user's authorization.
